# idv-login-webui handoff

## 1. Current state

This package is the Starward-aligned UI and motion revision of `idv-login-webui`, followed by a logic-focused compatibility review.

The current source and `dist/index.html` include:

- Starward/WinUI-aligned control sizing, spacing, surfaces, dialogs, and navigation.
- Pointer-local Reveal lighting, short Fluent state transitions, page/dialog/list transitions, and ProgressRing loading states.
- Process-lifetime launcher image URL caching and bounded image predecode retention.
- Logic guards added after the motion/design refactor to prevent stale asynchronous work from being applied to another game or dialog.

The deployable artifact is `dist/index.html`. It is a self-contained page generated by `scripts/build-standalone.mjs`.

## 2. Important behavioral invariants

Future changes should preserve these invariants:

1. **A game-scoped asynchronous operation must use a snapshot of `game_id`, `distribution_id`, and, when relevant, `installation_id`.** Do not read reactive current-game state after an `await` and use it as the target of an operation that began earlier.
2. **A stale response may finish on the backend, but it must not update the UI state of a different game.** `LauncherView.vue` and `GameSettingsModal.vue` use generation counters and scope comparisons for this.
3. **Only the topmost modal may respond to Escape, backdrop dismissal, or application-level keyboard submission.** The stack implementation is in `src/modalStack.js`; modal tokens remain stacked until the leave transition finishes. `AppDialogHost.vue` relies on focused-button native Enter behavior instead of a document-wide shortcut.
4. **Only one KeepAlive page is active during main navigation.** `App.vue` uses `mode="out-in"`; removing it can briefly activate two pages and duplicate polling or keyboard behavior.
5. **KeepAlive pages must stop timers when deactivated, and in-flight poll responses must not restart obsolete loops.** `SettingsView.vue`, `LauncherView.vue`, and `AccountsView.vue` use lifecycle cleanup plus generation/scope guards.
6. **An installation cannot start until disk capacity is known.** The shared calculation is in `src/installRequirements.js`.
7. **The backend's positive `required_bytes` is authoritative.** Otherwise use `max(unzip_bytes, download_bytes)`. A disk result of exactly zero bytes is a valid known result, not a loading sentinel.
8. **Image references are assumed stable for one process run.** `resourceUrl()` and image preloading rely on the user's stated invariant that a URL will not point to different image content during the same run.
9. **The standalone builder has an explicit module list.** Any new local JS/Vue module imported by the app must also be added to `moduleOrder` in `scripts/build-standalone.mjs`.

## 3. Logic review findings

### Accidental breaking changes introduced by the design/motion refactor and fixed

#### Nested modal keyboard propagation and lost backdrop dismissal

The motion pass added Escape handling to every `ModalShell`, while `AppDialogHost` also listened globally. With a confirmation dialog above game settings, one Escape press could close both layers. The first Starward dialog rewrite also removed the original backdrop-click dismissal.

**Fix:** `src/modalStack.js` makes dismissal topmost-only; `ModalShell.vue` restores backdrop dismissal, supports non-dismissible busy states, and retains the top token until its leave animation finishes. `AppDialogHost.vue` no longer has competing document-wide Escape or Enter shortcuts; focused controls keep native keyboard activation.

#### Two KeepAlive pages briefly active

The motion pass removed `mode="out-in"` to create an overlapping crossfade. That allowed old and new KeepAlive pages to remain active together during the transition, including their document listeners and timers.

**Fix:** main navigation again uses `mode="out-in"`. Visual movement remains, but business lifecycles do not overlap.

#### Installation-dialog path and capacity races

Moving installation into a persistent dialog made it possible to invoke path selection repeatedly and allowed an old path-status response to arrive after a newer choice. The first version could also expose installation before a valid capacity result existed.

**Fix:** only one picker is accepted at a time, stale path-status responses are discarded, the dialog is non-dismissible while native path work is pending, and installation requires a finite capacity result.

### Pre-existing logical defects uncovered and fixed during review

#### Game-switch races in launcher actions

The launcher component remains alive across game switches. The old `:key` was on the component's root DOM element, so it recreated DOM but did **not** recreate `<script setup>` state or cancel in-flight promises. An install, update, locate, start, remove, or Fever import begun for game A could therefore resolve after switching to game B and refresh or display its result against B. This race predated the motion pass; preserving launcher DOM for crossfades made it especially important to fix rather than assume the old DOM key provided isolation.

**Fix:** `LauncherView.vue` captures an operation scope and applies UI updates only while that scope still matches. Changing game or distribution invalidates path selection, download monitoring, and open game-specific dialogs.

#### Stale game-settings responses

The four settings requests could overlap when the game or installation changed. A slower response for game A could overwrite the form already showing game B.

**Fix:** `GameSettingsModal.vue` uses an immutable query snapshot plus `loadGeneration` and a full game/distribution/installation match before applying results.

#### Cloud-sync probe race

The master key and mode remained editable during `/cloud-sync/probe`. A result for an old key could advance the wizard after the form had changed.

**Fix:** probe input is locked while pending, the request captures key/mode/step, and generation checks discard obsolete responses. The wizard cannot be dismissed while save/probe work is pending.

#### KeepAlive polling and account workflow defects

- `SettingsView.vue` diagnostics polling continued while the KeepAlive page was deactivated. It now stops on deactivation and resumes only when active. A generation token also prevents an in-flight old poll from creating a second loop after rapid leave/re-entry.
- Account selections could survive a game switch and later be used for batch deletion in another game's account view. Selection is now cleared on game change and pruned against the loaded account list. The selected login channel is also cleared when the game changes or the channel is no longer supported.
- QR polling and account import now retain the game ID from the operation start, so a later game switch cannot retarget requests or apply stale QR state. Polling is serialized with recursive timeouts rather than overlapping `setInterval` requests, and leaving the accounts page cancels the native QR session instead of returning to a frozen modal.

## 4. Intentional compatibility changes

These are deliberate behavior changes and should not be mistaken for accidental regressions:

### Installation now requires explicit confirmation

The old flow was:

`Download game` → native directory picker → install starts immediately.

The current flow is:

`Download game` → installation dialog → choose/change directory → inspect capacity → press `Start installation`.

This adds one confirmation click and leaves the dialog open when directory selection is cancelled. It matches the reference project's installation-dialog model and reduces accidental installation.

### Disk-space validation is stricter

The old implementation compared free space only with `download_bytes`. The current implementation prefers `required_bytes`, otherwise the larger of compressed download size and unpacked size. It can reject an install that the old UI allowed when there was enough room for the archive but not for extraction. This is an intentional safety correction.

### Hidden download polling is slower

Download status is polled every 750 ms while visible and approximately every 1.8 seconds while the view or document is inactive. The backend task is unaffected; only background UI freshness is delayed by at most roughly one additional second.

## 5. Known architectural constraints not changed

### Global busy state

`useAppStore.js` exposes one global `state.busy`. A long native operation started for one game can temporarily disable controls after the user switches to another game. Scope guards prevent it from targeting the wrong game, but busy-state granularity remains global. Changing this safely requires deciding whether the backend permits concurrent operations and introducing per-operation/per-game busy keys.

### Game-ID suffix comparison

`cmpGameId()` treats IDs with the same final hyphen-separated segment as equivalent. This appears intentional for current backend IDs, but would collide if two unrelated games shared that suffix. Do not replace it without confirming the backend's canonical ID contract and persisted rail/cache migration behavior.

### Requests are invalidated, not cancelled

Generation checks prevent stale UI writes, but they do not abort already-issued HTTP/native tasks. Some backend operations, especially installation and update, are expected to continue in the background. Introducing AbortController or task cancellation requires endpoint-specific semantics.

### Optional endpoint detection

Several features treat HTTP 404 as “backend update required.” This is compatibility behavior for older native backends. Do not convert all 404 responses into fatal errors.

## 6. Architecture map

- `src/App.vue`: shell, main navigation, GameRail, connection state, toast/dialog hosts, motion system installation.
- `src/composables/useAppStore.js`: singleton reactive application state, game/account caches, launcher requests, navigation, guarded mutations.
- `src/components/LauncherView.vue`: launcher data presentation, install/update/start/locate/import actions, background task monitoring.
- `src/components/InstallGameModal.vue`: installation confirmation and disk-space gate.
- `src/installRequirements.js`: shared installation-capacity semantics.
- `src/components/GameSettingsModal.vue`: installation metadata and game-scoped launch settings.
- `src/components/AccountsView.vue`: accounts, default account, import/login/QR workflows, batch selection.
- `src/components/CloudSyncView.vue`: encrypted sync settings, action commands, setup wizard, probe/save concurrency.
- `src/components/SettingsView.vue`: global settings and diagnostics polling.
- `src/components/ModalShell.vue`, `src/modalStack.js`, `src/components/AppDialogHost.vue`: modal lifecycle and application dialogs.
- `src/motion.js`: event-delegated Reveal pointer tracking.
- `src/launcherCache.js`, `src/api.js`: visual metadata caching, bounded image predecode retention, and stable resource URL conversion.
- `src/style.css`: Starward design and motion tokens plus component styling.

## 7. Build and validation

On a clean machine matching the target platform:

```bash
npm ci
npm run check:sfc
npm run check:logic
npm test
npm run build
npm run build:standalone
```

Validation scripts:

- `npm run check:sfc`: parses and compiles all Vue single-file component templates.
- `npm run check:logic`: checks pure installation behavior and asserts that critical stale-response/lifecycle guards are still present.
- `npm test`: Vitest suite, including `tests/logic.test.js`.
- `npm run build:standalone`: rebuilds the self-contained `dist/index.html` without Vite/Rollup.

The supplied archive intentionally omits `node_modules`. The uploaded dependency directory was created for macOS arm64 and cannot load the Linux Rollup native module. Always run `npm ci` on the deployment/development platform.

## 8. Review checklist for future changes

Before merging a change to launcher, account, or cloud workflows:

- Capture all target IDs before the first `await`.
- Decide whether a stale response should be ignored, displayed as a background completion, or explicitly cancelled.
- Test switching games while every native picker or network request is pending.
- Test a confirmation dialog opened above another modal, including rapid repeated Escape presses.
- Test navigating away from diagnostics and back while a terminal request is in flight, verifying there is only one poll loop.
- Test navigating away from an active QR login and verify both the frontend timer and native QR session are cancelled.
- Test zero-byte free capacity, missing capacity, and `required_bytes` smaller/larger than unpacked size.
- Rebuild `dist/index.html`; source-only changes are not enough for the embedded deployment.
- Add any new source module to `scripts/build-standalone.mjs`.

## 9. Modal visual stacking invariant

Every `ModalShell` receives a monotonically increasing runtime z-index when it opens. This is required because Vue Teleport preserves component declaration order in the target DOM; equal fixed z-index values would otherwise let a modal declared earlier render below an already-open modal even when it opened later. Do not replace the runtime layer with a single shared z-index unless all modals are moved into one centralized stack renderer.

The ordering behavior is covered once in `tests/logic.test.js`. The earlier review build also duplicated the same assertion in `scripts/check-logic.mjs` and exposed `modalStackDepth()` from production code solely to support review checks. Both were removed: the production stack now exports only operations used by the application, and the standalone logic script no longer duplicates the unit test.

## 10. Proven-unreachable code cleanup

The latest pass removed only branches or APIs whose non-use can be established from the current program structure, without deleting backend compatibility or asynchronous race guards:

- Removed the unused alert-dialog variant and its permanently unreachable rendering/cancellation branches. The application only creates confirm and prompt dialogs.
- Replaced `setModalOpen(token, open)` with `openModal(token)` because no caller ever passed `false`; closing already has the separate `removeModal()` operation.
- Removed the production-only `modalStackDepth()` inspection API and the duplicate ad-hoc modal assertion from `check:logic`; the behavioral unit test remains.
- Removed the unused fetch-based `warmLauncherImages()` path. Runtime image work uses the bounded `preloadLauncherImages()` decode cache.
- Removed the unused store setter `setLauncher` and unused per-item values in the computed game rail model.
- Removed conditions that were dominated by earlier invariants, including the second `gameId` check in `selectGame`, the impossible null scope checks on locally captured operation scopes, and the redundant path predicate already implied by known installation capacity.
- Simplified pointer-leave cleanup where the second condition was the logical complement of an immediately preceding early return.
- Removed event-null handling from handlers that are only registered as native Vue pointer-event callbacks.
- Removed fallbacks for closed finite state sets (`app.state.view` and the settings section ID) after their input boundaries have already validated those values.

Defensive branches for backend errors, stale promises, modal leave transitions, repeated native operations, malformed persisted data, and race cancellation remain intentionally. Those paths may be uncommon, but they are reachable and must not be treated as dead code.
